# 07 · N 档 EXIF 的 k 值

> Status: 根因已定；官方 k=2 未修；项目内用 k=0 表示 N
> Evidence: 真机（V k=1 / N k=0）+ 静态（桩/分支）
> 适用范围：E-M10 II / E120 1400 0000 0000

## 问题

拍 V 档时 EXIF 写 `k=1`，拍 N 档时也写 `k=1`。是 N 没有自己的键，还是写 EXIF 时被改掉了？

## 原来的判断

早期认为 N 的键就是 1，和 V 撞车；后来发现更准确的说法是：

- N 的**图像选表**有独立路径；
- N 的 **EXIF 写键**在写之前被清成了 0；
- RELEASE_v1 对无效 k 选择“跳过写”，于是留下上一张的旧值。

## 结果

### 1. key 的来源

key 由 `ctx+8..0xB` 组装：

```text
key = u8[ctx+8]<<24 | u8[ctx+9]<<16 | u16[ctx+0xA]
```

源头是 `src+0..3`。V/N 送进来的头 4 字节都可以是 `00 00 01 00`。

### 2. SD 桩把 key=2 清掉

原厂 SD 桩（`0x605DED44`）：

```text
mov d1,d2
mov 0x605DED70,a0
mov d2,(a0)
cmp 2,d2
bne +4
clr d0
mov d0,(a0)
jmp 0x604B8124
```

也就是：key==2 时把 stash 清 0。
N 的真 key 很可能是 2，但到 SU 桩时读到的已经是 0。

### 3. RELEASE_v1 跳过无效 k

SU 桩算：

```text
k = ((key>>24)&3)<<3 | (key&7)
```

`k=0` 时 `k-1` 无符号 >3，跳过写 EXIF。
所以旧 N 照片里看到的 `k=1` 是**上一张的旧值**，不是 N 算出来的 1。

### 4. P40b 真机

P40b 在 SU 汇合点读 stash 并写 EXIF：

- V：`k=1, key=1`
- N：`k=0, key=0`

这证明：

- P40b 确实执行了（否则不会写 0）；
- N 的 key 在到达 SU 前已经是 0；
- `k=0` 不是官方值。

## 影响

- 项目内约定：**V=1、N=0、M=3、P=4**；
- `k=0` 只用于本项目辨别档位，不保证外部软件兼容；
- 官方 `k=2` 仍未修；P40c 需要保留 key=2 或提前暂存，未做；
- 发行补丁 `RELEASE_v1` **不包含** P40b 的 `k=0` 修法。

## 被推翻的结论

- “N 就是 key=1” → 不准确；N 的真 key 很可能是 2，被清掉。
- “旧 N 照片 k=1，所以 N 写对了” → 错；那是上一张残留。
- “k=0 是官方 N 值” → 错；官方枚举是 2。

## 证据与未证

- 真机：V/N 各一张，k=1 / k=0；
- 静态已证：SD 桩清零、SU 桩跳过无效 k；
- 未证：官方软件对 k=0 的兼容性；N 的真 key 在清掉前的值（推理为 2）。
