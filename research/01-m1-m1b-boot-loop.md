# 01 · M1/M1b 为什么重启

> Status: 已定论（历史事故复盘）
> Evidence: 真机（两包都上机、都重启）+ 静态（段表/装载器/字节对比）
> 适用范围：E-M10 II / E120 1400 0000 0000

## 问题

M1 和 M1b 都曾上机，结果都是开机后反复重启。最初怀疑是“读卡失败”或“fileif 不能跨任务调用”。实际不是。

## 原来的判断

M1b 的桩只有 70 B，被当成“marker / 占位”，M1 是 880 B 完整桩；当时认为 M1b 可能没真正执行，M1 才是真探针。

## 怎么查

1. 对原厂、M1、M1b、RELEASE_v1 做容器解码，按 RAM 地址逐字节对比；
2. 看两包的钩点、桩地址、段表装载范围；
3. 用真机现象反推：两包都在第一次 tone 上传后重启。

## 结果

两包的共同点不是“桩大小”，而是**跳转目标相同**：

- 钩点 `0x60479A2B`：
  - RELEASE_v1：`dc a9 52 16 00` → `0x605DECD4`
  - M1 / M1b：`dc 2d 92 1f 00` → `0x60672C58`
- `0x60672C58` 位于 `0x60662000..0x60673000`。
  - seg3 的 `used_end` 是 `0x60662000`；
  - seg4 从 `0x60673000` 开始；
  - 这个区间**不被任何段拷贝**。

所以：桩虽然在容器文件里，运行时不在 RAM。第一次 tone 上传执行到钩子，跳到未初始化内存，取指异常/看门狗 → 重启。

两包的差异只是：

- M1b = RELEASE_v1 + 3 B 钩位移 + 70 B 桩；
- M1 = RELEASE_v1 + 同 3 B + 880 B 桩；
- 两包相对差 837 B，不是重启原因。

## 被推翻的结论

- “M1b 没上机 / 只是 marker” → 错；两包都上机。
- “重启是读卡失败” → 错；根本没走到文件 I/O。
- “文件里有桩，就能执行” → 错；文件存在 ≠ 被映射 ≠ 可执行。

## 影响

- 之后所有桩位必须先过 `check_stub_region`，并且要证明“装载器会拷贝到”。
- 从 seg3 代码调用的桩只能放 seg1/2/3/7；seg4/5/6 的空洞不能当口袋。
- 后续可用的稳定桩位改为 `0x605F2600`（seg3），不再用 `0x60672C58`。

## 证据与未证

- 真机：两包都重启；
- 静态已证：钩字节、段表 `used_end`、装载器只按 `used_end` 拷贝；
- 未证：具体取指异常到看门狗之间的指令级时序（不影响根因判断）。
