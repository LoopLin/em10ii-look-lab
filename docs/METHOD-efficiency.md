# 方法红线：别再走"刷机试验"的路（2026-11-15 立）

> 由来：第一代把"刷机→拍照→看"定为默认验证方式，第二代、第三代沿用了这条路径，累计约 100 个固件包。
> 结果不是没进展，而是**每次刷机只回答一个问题**，而问题有几十个。用户已明确：效率很重要。
> 本文件是硬约束，写给第五代看；与它冲突的旧文档一律以本文件为准。

## 一、一票否决：没有离线预测，不许刷机

任何"刷一次看看"的提案，必须先交出**同一份参数的离线预测**（`tools/rawpipe.py` 渲染图 + 与预测值的差）。
交不出预测 = 不做。理由：真机图没有对照，只能靠眼睛，"变了"与"变对了"分不开。

## 二、一次刷机 = 一个已定稿的包，不是一次实验

- 刷机前所有候选必须在离线管线里比过、选过、定稿。
- 真机刷机只做**确认**（预测 vs 实测差 < 2/255），不做探索。
- 需要探索多个假设时，用"一包多候选"（21 条签名曲线 / 多档各自一套），一次刷机回答多个问题。
- 每次真机实验必须能在 **≤1 次刷机**内回答至少一个"答错就改方向"的问题；答不了的问题不许占用一次刷机。

## 三、"判死"只能由机制证据给出

- 允许说"不存在"的唯一依据：**反汇编证明调用路径不存在**（没有调用点 / 分支恒假且无写者）。
- "我改了没反应"只能写成「**在该模式下未观测到**」，并注明确切拍摄模式、档位、参数。
- 每份文档里的结论必须标证据等级：`真机` / `模拟器` / `静态` / `推理`。四条混着写的段落，按最低那条算。

## 四、当前闭环的定义（判据链）

```
look 规格(.json) → rawpipe 离线渲染 → 与参考(富士 cube / 官方 JPG)比 e1h
                                    → 定稿
                                    → 一次刷机
                                    → 真机 JPG vs 离线预测（< 2/255）→ 闭环成立
```

闭环没成立之前，任何"通道打通"的结论都不进交付物。

## 建包铁律（2026-11-15 用户立规）

1. **一包一根**：任何包都只从 `<official-firmware>.BIN` 出发构建；**禁止在上一个 BIN 上继续打补丁**（B30 就是这么坏的：探针表被继承进 look 包）。
2. **表与桩都从源来**：桩从 `.s` 汇编（`.tmp/*.s` → `objcopy`），不从旧 BIN 里拷字节；表从 `.tmp/looks_beta/*.json` 生成。
3. **每次出包前跑三道门**：
   - `t0/t1` 的 18% 值必须与原厂一致（584 / 804）；
   - 目标 look 表逐项核（22–25 槽的 `T[46]` = 689 / 651 / 642 / 716）；
   - 容器级 diff：改动字节全部落在声明区间内，区外 0。
4. **不许把测试表留在包里**：探针/阶梯表出完必须从包里消失（B28 之后的探针残留就是反例）。
5. **开工前先读坑表**：`docs/chat/POSTMORTEM-hook-2026-11-15.md`（判别量瞬态清零、分支目标不可插、FF≠可用、写入页只读风险、跨靶图比较无效……），再动手。

## 省 token 的四条（2026-11-15 复盘，按效果排序）

1. **一包多问**：同一个包尽量塞多个可判读维度（如"四档 + 矩阵 + 守卫"同包），把"刷机→拍照→读图"的轮次压到最少。今天 20+ 个包、40+ 张照片，一大半是单问单包造成的。
2. **离线门一次跑完**：`patch_check` + `audit_beta_pack` + libsim 三件合成一条命令跑，不要每改一字节就重跑一遍。
3. **长分析外包**：主线程只做决策与结论，逐字节验证、照片统计、文档检索交给子智能体（它们的过程 token 不进主上下文）。
4. **不重读、不整包 diff**：只 diff 声明区间；开工先读 `docs/SUMMARY-*.md` 与 `docs/POSTMORTEM-*.md`，不要重读全部 docs。

2. 容器能被 `oly_container` 解析；

4. `audit_beta_pack.py` 报 `[OK]`。

```bash

python tools/flash_gate.py build/<firmware>.BIN --copy
```

写卡成功会往 `docs/firmware/FLASH-LOG.md` 记一行（时间/包名/sha 前 16 位）。

**验证类包必须带探针（2026-11-17 第四代建议，用户采纳）。** 凡是以“验证某处有没有生效”为目的的包，必须同时带一条可回读的 EXIF 记录（字段与写点见 `docs/EXIF-PROBE.md` §5，读回用 `tools/read_probe.py`）；没有探针的验证包，判读结论只能当**弱证据**，不得据此判死或定案。探针与功能同包、记录点放决策点、不改变画面。

**模拟能证明什么、不能证明什么**（写进判据，避免又一次自欺）：

- 能证明：给定进入条件，链路上的字节真的按设计流动（桩被执行、k 被算出、表被选中、dest 里确实拷进了这张表）。
- 不能证明：真机会以这组条件进入这段代码。模拟里 `ctx+8/+9/+0x0A` 是我们 poke 的；真机这些字节从哪来、是不是这几个值，只能靠真机。

## 二次核验（硬性规定，2026-11-16 用户定）

**任何一个包，不管是主线程出的还是子智能体出的，上卡前都必须独立再过一遍。**

四道工序分工：

| 工具 | 查什么 |
| :-- | :-- |
| `tools/audit_beta_pack.py` | 数据本身合不合法（校验和 / 三锚点 / 表的形状） |
| `tools/patch_check.py --reach` | 钩点在静态分支上可不可达 |
| libsim（`verify_b*.py`） | 代码路径跑不跑得通、`closed` 是否 true |
| **`tools/second_verify.py`** | **这个包到底是什么**：独立重算尺寸/校验和/锚点、逐字节 diff 分段、落点是否越界（含不可用区）、**代码段变化处重新反汇编并独立算出跳转目标**、tone 池单调性 |

用法：

```
python tools/second_verify.py build/Bxx.BIN --base build/Byy.BIN
```

- `--base` 填上一版或 `<official-firmware>/…BIN`；不给就跳过 diff。
- 判据：`结论：PASS`（可以带 WARN）才许上卡；出现 `FAIL [zone]`（落在不可用区）或 `FAIL [checksum]` 一律不许上卡。
- 槽 52/53 的 tone WARN 属预期（被桩与色度块征用），其余 WARN 要逐条看。

这条规矩的由来：2026-11-16 连续出现"子智能体自检通过、但实际改错了地址/改多了字节"的情况，靠人工复核才发现。

## 每个包的固定说明（2026-11-17 用户定）

任何交付的固件包，必须同时给出四段，缺一段不算交付：

1. **改了什么**：与 stock 的差异清单（地址、字节数、语义）。
2. **为什么**：这个改动基于哪条证据/假设，要回答什么问题。
3. **预期是什么**：真机上应当看到的具体现象（可判读、可证伪）。
4. **与预期不符时，最可能的原因**：至少列出两三种分支解释，以及下一步怎么区分。

同时：**每个包都从 stock 起，不在上一版上改**，避免错误逐代累积；与上一版的差异用 `second_verify.py --base` 核对，确认只包含本包声明的改动。

## 链路地图法（2026-11-17 定）

任何"改哪条链"的问题，先只读铺地图，再谈补丁。色度（B63–B67）的教训换来的顺序：

1. **穷举调用点**：一个函数有几个 caller/callee，写清"只有 N 处"。只找到"一个地址"不等于找到"一条链"。
2. **分三层**：
   - 内容层：表里放什么（改内容通常 = 全局）；
   - 指针层：谁决定用哪张表（改指针才能每档）；
   - 链层：数据被谁消费、去哪（预览链 / 出口链，改错链 = 改了但画面不变）。
3. **五栏地图**，每条候选链填满：

   | 栏 | 问题 |
   | :-- | :-- |
   | 数据从哪来 | 静态表，还是运行期构造？ |
   | 谁选它 | 有选择器/指针表，还是写死？ |
   | 何时 | 每帧 / 切档 / 开机一次？ |
   | 谁消费 | 预览链还是出口链？进哪个结构？ |
   | 门 / 死支 | 标准档走到这一步吗？钩点会不会永不执行？ |

4. **证据分级、未闭合单列**：静态（反汇编/字节扫描）、模拟、真机、推理分开标；推理必须写清缺哪条证据。
5. **先地图后补丁**：地图没画完不出包；出包按四段式说明。

由此得到的判据：
- "静态表能改" ≠ "运行时读它"；
- "改完画面没变"，先查钩点是否可达、是否落在死支，再查是不是改错了链；
- "改内容变了"只说明表被读，不说明能分档。

案例：`docs/map/chroma-capture-chain.md`（选择器 / 出口链 / 预览链的三层地图）。

## 复查（2026-11-18 用户强调，B78 事故后加）

任何包在过四道门之前，必须做一次「基线差异审计」：

1. 选定的基线（通常是上一版完整包或 stock）写进构建脚本，不靠记忆。
2. 构建脚本必须从基线的 patch 文件**复制**再追加，不允许另写一份新 patch（B78 就是把 B69 的补丁行整个漏了）。
3. 审计输出两样东西：与基线的全部差异区间；逐条对照的预期清单（本包新增的钩/桩/表 + 基线本来就该有的全部补丁点）。
4. verifier 必须断言基线补丁点仍在（SU 钩/SU 桩/SEL 钩/SD 钩/色度块/EXIF 文本等），只验新字节不算过。
5. 没有差异清单的包，不许上卡。

## 双模拟器 + 复查（2026-11-18 用户强调，B81 事故后加）

任何新固件，**必须两个模拟器都过、再做一次复查，才允许上卡**；少一道都不行。

1. **libsim**（`tools/verify_b*.py`）：`closed=True`，覆盖代码路径、字节、寄存器契约；探针类包必须从真实入口跑（不是只从桩起点跑）。
2. **整机 MN10300 harness**（`tools/em10_run.py`）：用 `--image` 载入补丁包，从真实入口跑关键路径，确认不 fault、分支落点正确；`--breakpoint` 用来验证每条分支。
3. **复查**：按上一节五条差异审计走一遍，输出「基线差异区间 + 预期清单」，逐条勾掉。
4. **探针包额外一条**：钩点必须回答“被测模式从哪条路进来、这条路上是否经过该地址”，并在这条路上跑通；只验桩本身不算过（B81 把钩子挂在标准档根本不调用的选择器上，就是反例）。

两条模拟器 + 复查三样齐全，`flash_gate.py --copy` 才允许写卡；缺一样就停在离线。

## 模式开关类改动（2026-11-18 四代建议，B82 事故后加）

凡是会改变“相机当前处理模式”的补丁（`ctx+0x0C`、`ctx+0x10`、`ctx+0x24A`、`ctx+0x3C0` 这类字段），必须满足：

1. **只在目标档命中时改**；其它档必须原样恢复，不能“顺便”改到公共路径。
2. **配套结构一起准备**：ISP 的分区模式不只看那几张表，还要系数区、缓冲布局、完成信号；只翻开关不铺路，一定出事（B82 的连带花屏就是例子）。
3. **探针记录改动前后**：改之前的值、改之后的值、改了几次，进 UserComment；没有记录的开关类包不许上卡。
4. **给建议时同时说明会破坏什么、怎么验证没破坏**，不能只说“只改一个字段”。

## 落点启用清单（2026-11-18 用户要求，B84 事故后加）

任何包在选落点（钩点跳过去的地址、或表/结构放的位置）时，先按这张清单逐条打勾，**没有清单不许出包**，清单原文贴进四段式的「改了什么」后面。

| 检查项 | 判据 | 证据 |
| :-- | :-- | :-- |
| 1. 在加载范围内 | `[段起, 0x60DA5000)` 之内 | 静态（加载器范围） |
| 2. 离段尾距离 | 贴 `0x60DA5000` 的一律当栈，不用 | 真机（B14b/B15/B45） |
| 3. 引用普查 | 无指针/立即数引用；`patch_check.py` 或引用扫描为 0 | 静态 |
| 4. 是否被开机/运行期写 | 只能靠小步真机实验，模拟器零信息量 | 真机 |
| 5. 大小预算 | 口袋大小 − 现有占用 ≥ 本包需求，且留余量；槽 53 的 ≈200 B 只是“不碰 ART”的预算 | 静态 + 文档 |
| 6. 该口袋在本路径验证过 | 旧路径的 PASS 不继承；新路径 = 新证据 | 真机 |
| 7. 代价声明 | 占了哪张 ART 表/哪个模式会坏、ISP 系数区是否相邻，写进四段式 | 静态 |

判定原则：

- **「可用」是路径限定的**，不是全局属性（案例：`0x601ADE04` 在矩阵路径活、在 HSL 门路径炸，B84 语义等价仍炸）。
- **模拟器只证明指令语义**，不证明落点在真机上的归属；落点问题只能用真机小步实验分离。
- **一次只验一件事**：落点验证不要和功能改动塞进同一包；若必须同包，钩/桩必须语义等价、不引入第二变量。
- 越界使用口袋（如槽 53 超过 200 B）不是禁止，但必须显式声明 ART 代价，不能写成“无代价”。

## 取样与量化（2026-11-18 用户定，噪点照片）

- 照片有噪点，**禁止取单像素**；一律区域统计：取色块中心区域的中位数（不是均值），同时记录区域内标准差 σ 作为噪点水平。
- 色卡类：先用 `tools/chart_sample.py` 自动找黑框与 6×4 色块，逐块取中心 25% 区域中位数；输出 RGB 与 σ。
- 比较两图同一块：转 Lab 后算 ΔE；ΔE 小于两图 σ 换算的噪声底（约 1–2）时，只能写“无可测差异”。
- 灰阶/曲线：用覆盖 0–255 的斜坡图，并检查残差随亮度的分布；只用中间调拟合时必须标注“近似”。

## 子智能体交付必须二次验证（2026-11-18 用户要求）

任何子智能体交回结果，我都要独立复核后才能采信或继续下一步。复核清单：

1. **数字复算**：从交付文件（JSON/CSV/脚本）重跑关键统计，不抄报告里的数；至少抽 2 个样本或 1 个场景全量重算。
2. **路径一致**：确认评估、预览、交付参数走的是同一个渲染/计算函数；跨 look/跨场景的缓存要能逐项校验（例如回读图片与模型输出逐像素比对）。
3. **参数合法性**：矩阵行和、奇偶约束、tone 单调性、色度折线端点、槽位大小、落点占用——逐项用脚本断言，不靠“它说合法”。
4. **文件与血缘**：sha256、输入清单、种子、划分（训练/验证/定性）可复现；产物路径与报告一致。
5. **结论与证据等级**：每条结论标“实测/静态/推理”，与数字对不上的一律降级或打回。
6. **不一致先停**：发现报告数字与复算不符，停止后续调参与出包，先定位差异（本次 preview 缓存 bug 就是漏了第 2 条）。

这条与「验证类包必须带探针」「查前先交子智能体」并列，作为交付前的硬门。

## 状态分类（2026-11-19 用户定）

汇报与文档里，状态必须分开写，**禁止把“未开工”和“已判死”合并**：

1. 已闭环（真机可复现）
2. 未闭环（有代码/模拟，未真机）
3. 未开工（还没碰）
4. 已判死（有明确阴性证据，比如标准档 HSL、Classic Neg 模型上限）
5. 搁置（决定暂不做）
6. 受限（受落点/空间/时间盒约束）

合并这两类会让人误以为“还没试”或“已经试死”，两种误读都会浪费一轮。

## 固件命名（2026-11-19 用户定）

## 落点三件事（2026-11-19 定，L10a v1 开机重启后加）

任何新落点（桩/表/数据）上机前必须三件事齐备：

1. **静态零引用**：目标区 `FF` 游程 ≥ 所需长度，且全镜像无 imm32/指针引用；
2. **动态哨兵**：在候选地址写 `DEADBEEF`，emu 跑开机+取景，确认不被改写（`FF+零引用` ≠ 运行时不写；L10a v1 的 `0x601F8400` 就是这么炸的）；
3. **归属 diff**：与基线逐字节差异必须全部落在登记的区间；否则先解释再上卡。

配套教训（详见 `docs/incidents/2026-11-19-pitfalls.md`）：键表插槽会破坏线性探测的其它键（L8/L9a，ART1 子挡位 2 与 ART10 重启）；改 cell 无效（产帧对象键被硬写 2，`0x604AA276`）；ART tone 共用 g0 但上传器旁路桩可按键换二级表（B59/B95 的生效通道）。

## 读结构先读读者（2026-11-20 定）

写任何结构字段之前，先反汇编**读它的那段代码**，按它的取字节顺序/符号/单位解，不要按"看起来像"去假设布局。

反例（同一类错误，三次）：B63 假设 `ctx+0x37D8` 是成片色度源；L8 往键表插了个槽；L16 把 `ctx+8..B` 当 32 位小端读（实际是 `byte0<<24|byte1<<16|u16`）。三次都不是"钩不住"，是"读错了布局"。

检查清单：① 找到消费点；② 抄它的 load 序列；③ 用该序列的语义写测试值；④ 再用真机确认。
- **2026-11-21 用户定**：固件做好、复审、审计（四道门）之后**直接写卡**，不再每包问一次；写卡仍只经 `tools/flash_gate.py`。

## 单一真相源（2026-11-21 定）
