# 预览链（LV/EVF）× 成片链（JPEG）：分岔点、补丁可见性、Portrait 偏灰

> 2026-11-21 复核版。**替换 2026-11-19 版**：旧版结论「取景帧 mask 从不置 0x8/0x10000 ⇒ 预览从不推 look」与真机 B60/B68 冲突，作废（错在读「mask 从没置位」，实际 mask 每帧被清零后由模式处理器重设，且预览走的是同一套模式应用）。

## 0. 结论先行（5 条）

1. **分岔点 = `0x604B4B24` 的两个调用点**：`0x604AA297`（预览侧）与 `0x604B4E29`（成片侧）。全镜像**只有这两个**外部调用者。【核实】
2. **分岔前是"同一份参数池、零拷贝"**：getter 直接返回池块指针（path ① `a0 = *(ctx+0x3C0); add 0x1D,a0; ret`）。分岔后才各自拷贝成不同形态——预览 `0x9C` B 原样 → `out+0x1D`；成片重排成 16×u32 → `obj+0xA4`、16×u32 → `obj+0xE8`。【核实】
3. **但预览帧会走进成片同款"模式应用"序列**：LV 帧 `0x6046AAB6` → `0x6046E9B5`（class 3）→ 快路不成立 → `0x6046EDC0` → `call 0x6046EAAF` → {矩阵链 `0x604B500E`、色度链 `0x604AF0A9`}。【核实】
4. ⇒ **四档 look 的四个改动点全部在预览路径上被读到**。tone/弯曲靠共享上传器 `0x60479960`（预览直接调 `0x60477F4C`），矩阵/色度靠 `0x6046EAAF`。**结论：0 B 自动一致**（§5）。
5. **Portrait 偏灰不是参数搬运问题**。静态已排除两项（§4）：① "预览读库存色度块"（偏离幅度排序与之相反）；② "预览不推 tone"（上传器共享且钩点在上传器内部）。剩余候选在显示侧，与我们的补丁无关（前提：Portrait 不在四档槽内）。

## 2. 问 1：两条链在哪一步分岔？分岔后读同一份还是拷贝？

**分岔点 = `0x604B4B24` 的两个调用点。**【核实】

| | 预览侧 | 成片侧 |
|---|---|---|
| 调用点 | `0x604AA297` | `0x604B4E29` |
| 字节 | `DD 8D A8 00 00 F0 18` | `CD FB FC F0 18` |
| 所在函数 | `0x604AA228`（唯一 caller `0x6048379B`） | `0x604B4D25` 内（caller `0x604AF0E0` ← `0x604AF0A9`） |
| 分岔后形态 | `mov 0x9c,d1` 循环 → `out+0x1D`（0x604AA30E..31C） | `obj+0xA4[16]`、`obj+0xE8[16]`（0x604B4E42..0x604B4ED6） |

- 全镜像 xref：`0x604B4B24` 的外部调用者**只有** `0x604AA297` 与 `0x604B4E29`。区间内的 `0x604B4C8B`/`0x604B4CFA`/`0x604B4CFD`/`0x604B4D08` 都是它自己的内部标签（调用者落在 `0x604B4B7x–0x604B4C06` 自身）。
- **分岔前不拷贝**：path ①（`0x604B4B31`/`0x604B4B33`）= `mov 0x3c0,a1; add a3,a1; mov (a1),d0`；非 0 时 `a0 = *(a1); add 0x1d,a0; ret` ⇒ 返回的是**池里那个块的指针**，`0x604B4E29`/`0x604AA297` 拿到的是同一个地址。
- **分岔后各拷一份**：预览把 `0x9C` B 原样搬走（`mov 0x9c,d1` 循环）；成片把它拆成 16 项 24-bit（`movbu (d1,a0)` / `(a0+4,d1)` / `(a0+0x21,d1)` 三字节拼 `(4+4*i,obj+0xA4)`，`i<0x10`），另用 `a0+0x32/0x42/0x52` 拼出 `obj+0xE8` 的 16 项，`asl 0x10` 取 `(0x20,a0)` 写 `(a3)`，末尾 `and 0xfffffffd` 清 `(a0)` bit1。
- **`0x9C`=156 B 与两个 16 项表尺寸吻合**：16×3（+0x00/…）+ 16×3 + 16+16（+0x20/+0x21 起两段 y）≈ 156。

**分岔点为什么正好在这里**（不是更上游）：两条链在 **ISP 装配 `0x60477F4C` 与上传器 `0x60479960` 上是共用的**（§3.3），差异只发生在"把池块搬进哪个消费者的结构"这一步。

## 3. 问 2：我们改的四处，预览链读不读到？

### 3.1 关键前提：LV 帧确实会跑成片的"模式应用"【核实】

`0x6046ED33`（class 3 = 取景）的快路条件是 `(8,a1)==0x702/0x703` + 一串 u16 相等 + `(4,a2)==0`：

```
6046ED42  cmp 0x702,d0 / 6046ED48 cmp 0x703,d0
6046ED4E  mov (4,a2),a1 / 6046ED51 cmp 0x0,a1 / 6046ED53 bne 0x6046edc0
6046EDB5  F8 E4 04        or 0x4,d0        ← 快路只置 mask bit 0x4（不含 tone 的 0x8/0x10000）
6046EDB9  CD 2D 2C F0 14  call 0x604719e6
6046EDC0  CD EF FC F0 18  call 0x6046eaaf  ← 兜底：成片同款"模式应用"
```

`0x6046EAAF` 内部（a0=d3 一路传下去）：

```
6046EAE1  F1 EC              mov d3,a0
6046EAE3  DD 53 B8 03 00 F0 AC  call 0x604aa336      （model 入口判据）
6046EAEA  F1 EC              mov d3,a0
6046EAEC  call 0x604b500e    → 矩阵链 0x604BAB14 → 0x604BA774（含矩阵门 0x604B6AD6）
6046EB04  F1 EC              mov d3,a0
6046EB06  DD A3 05 04 00 20 08  call 0x604af0a9      （色度链）
6046EB0E  call 0x60473c12
```

`0x604AF0A9` → `0x604B5036/0x604B503D/0x604B5093` → `0x604BAB14` → `0x604BA774`（矩阵门 + 弯曲门 `0x604B9F1F` 所在 `0x604B9EBF`）；`0x604AF0A9` → `0x604B4D25` → **`0x604B4E29`（成片侧那条 getter 调用）**。

⇒ **`0x6046EAAF` 是两条链共用的"模式应用 + 参数落位"函数**，它的三个 caller 是 `0x6046AA7D`（成片派发）、`0x6046EC56`（成片 default 支）、**`0x6046EDC0`（取景 class-3 兜底）**。

### 3.2 逐项

| 我们改的 | 落点 | 预览是否读到 | 证据 |
|---|---|---|---|
| **tone 表指针** | 钩 `0x60479A2B`（`mov (a0),d0`，`a0=(4,SP)+0x1230`）→ SU/SD 桩 → 指针表 `0x605DEDD4` | **读到**（强） | `0x60479A2B` 在 **tone 上传器 `0x60479960` 内部**；该上传器全镜像只有 2 个 caller（`0x60478A73`/`0x60478A95`，都在 `0x604789CF` 内），而 `0x604789CF` 的唯一 caller 是 **`0x60477F4C`，取景帧 `0x6046AAB6` 在 `0x6046AB50` 直接调它**。mask 只决定走 ch0(`0x9E00A400`)/ch1(`0x9E00CC00`)，不决定用哪张表。**即使预览帧没置位、不重传，ISP 里留着的也是上一次传进去的我们那张表** ⇒ 两种情形都一致 |
| **弯曲门** | `0x604B9F1F` C8→CA | **读到**（强） | 弯曲函数 `0x604B9EBF` 唯一 caller `0x604BA81B`，在 `0x604BA774` 内；`0x604BA774` ← `0x604BAB14` ← `0x604B500E` ← **`0x6046EAEC`（= `0x6046EAAF` 内，预览可达）**。且它改的是 `*(S+0x1230)`——正是 `0x60479960` 上传时读的那个指针 |
| **矩阵指针** | 钩 `0x604B6AD6`（MX 桩 `0x601ADE04`，表 `0x605DEE3C`） | **读到**（强） | 矩阵门 `0x604B6AD4/0x604B6AD6` 在 `0x604BA774`；同上链：`0x6046EAEC call 0x604b500e` → `0x604BAB14` → `0x604BA774`，预览可达 |
| **色度块** | 钩 `0x604B4CAD`（`FC DC 29 48 5D 60` = `mov 0x605D4829,a0`，6 B）→ SEL 桩 → 表 `0x605DEDE4` / 块 `0x605DEB44+0x64*(k-1)` | **读到**（强） | 钩点**在共享 getter `0x604B4B24` 内部**（`0x604B4C8B` 的越界兜底路径），getter 的两个消费者都经过它；预览侧经 `0x6046EAAF → 0x604AF0A9 → 0x604B4D25 → 0x604B4E29 → getter` 进入。**真机 B68 直接印证**：色度随档变，预览+成片一起变、不重启 |

### 3.3 三个"当年被误判"的点（附纠正）

1. `0x605DEDD4`/`0x605DEDE4`/`0x605DED1C`/`0x601ADE04` 在**镜像里没有任何 u32 指针引用**（`refs.py` 全 0 命中）——因为它们在 stock 里不是表，是自由空间：stock 在 `0x605DEDD4` 处是 `1b 01 20 01 25 01 2a 01 2f 01 34 01 39 01 3e 01`（普通字节），是补丁种进去的。**不是"xref 丢了"，是本来就没有**。【核实】
2. `0x60479960` **只有一个上传器、两套窗口**，由 mask bit `0x8`/`0x10000` 选 ch0/ch1。"预览有一套自己的上传器"是错的。【核实】
3. `0x604B4CAD` 处的 stock 立即数是 **`0x605D4829`**（`FC DC 29 48 5D 60`），不是 `0x605D4800`（`0x605D4800` 是同函数里另一条路径的基址，`0x604B4CB3` 起拿它做表基址查 `0x605FFDC8`/`0x605FFE28`）。【核实】
4. `future-needs §3.3` 的「`0x6047FD3D` → 16×y → `R+0x102/+0x112`」：`0x6047FD3D` 里 `0x102`/`0x112` **一个立即数都没有**；实际是 `R+0x102 = O+0x3872`、`R+0x112 = O+0x3882`，由 `0x6047FEC6`/`0x6047FECB` 从 `slot1+0x2D`/`slot1+0x5F` 各拷 16 次 y 写入（见 `chroma-consumers.md`）。**那句要降级**。【核实】

## 4. 问 3：Portrait 下预览更灰，最可能来源

### 4.1 静态能排除的（已排除）

| 候选 | 结论 | 依据 |
|---|---|---|
| ① 预览读库存色度块、成片读我们的 | **排除** | 四张块相对库存块（`0x605D4829`，100 B）的 mean\|Δ\|：k1 **45.95**、k2 **54.97**、k3 **57.67**、k4 **53.15**。若是"预览读库存"，偏灰幅度应与之同序（Muted 最大），而真机观察是 **Portrait 最大** ⇒ 排序不符 |
| ② 预览不推 tone（旧 preview-chain 的说法） | **排除** | 钩点在唯一上传器 `0x60479960` 内部，且取景帧直接调 `0x60477F4C`（§3.2）。即使不重传，ISP 保留的也是我们的表 |
| ③ 硬件缩放/降采样导致"另一条曲线" | **排除**（对表内容而言） | 上传的是 **16 项的 y 表**（0x9C 块），不是直方图、不是像素；`0x604790A2` 拷的是 `src+0x88..0x178` 常量块，与分辨率无关。缩放只会改变"用哪些表项"，不会改变表 |
| ④ 两条链读不同参数对象 | **排除** | §2：getter 只有一个、返回同一份池块指针 |
| ⑤ 我们的四档 look 本身在 Portrait 上偏离库存最大 | **排除** | 见 ①的数字，k4 只排第三 |

### 4.2 最可能（按可信度）

**A【推断·强】预览侧的色度是被"每帧清零 + 受门控的回填"剥掉的。**
- `0x6046E9DC`（唯一调用点 `0x6046E9BE`，在 `0x6046E9B5` 内，取景帧 `0x6046AB03` 每帧调一次）把 **`model+0xA8..model+0x118` 共 28 word 清 0**（另清 `model+0xE0`、`model+0x00` maskA、`model+0x04` maskB）——`model+0xA8..+0xE4` / `+0xEC..+0x118` 正是成片侧 `obj+0xA4`/`obj+0xE8` 那两个 16 项表的落点（`0xA8 = 0xA4+4`，`0xEC = 0xE8+4`，与 `(4+4*i,obj+0xA4)` 完全对齐）【核实布局；"obj == model" 为【推断】】。
- 回填 `0x604B4E42` 前面有 5 道门：`btst 0x3,*(ctx+76)`（`F8 00 4C`/`F8 EC 03`/`C9 05`，不置位就 `jmp 0x604b4dca`）；`d0=*(param)>>4&3 ∈{1,2}` 时跳 `0x604B4DDF call 0x604b4cfd`（占位 `0x800000`，**中性**）；`btst 0x120202f,*(a3+0x38)`；`(5581,a2)/(5582,a2)` 与 `(76,a1)&3`/`(param>>4)&3` 比对；`*(960,a0)==0`。任一不满足就 `0x604B4E26 ret`（**一个字节都不写**）。
- ⇒ 若某一档/某状态下这几道门在**取景帧**与**成片帧**取值不同（取景侧参数块是 `0x60473994` 搬进 `buf+0x94` 的拷贝，头字 `0xF005`、类字节 3，与成片的帧对象不同源），预览就会拿到 **全 0** 或 **`0x800000` 中性**，而 JPEG 拿到真块 → 预览灰。**这能解释"某几档灰、其它档不明显"**（门依赖档/状态），也解释不了 B68（见 4.4）。

**B【未证】显示侧自己还有一级 tone/gamma。** 取景独占 `0x60479D0C` 写 `0x9E000000/08/10/18/68/6C/70/74/120/128` 一组显示描述符（按 `ctx+189` 二选一，`0x80001201/0x20A01/0x341/0x101008/0x800` vs `0x2404000/0x200A01/0x2141/0x40100000/0x1040`），且 `0x60479B92` 按 `ctx+0xBD`/`ctx+189` 选 ch0/ch1。**若 EVF 面板链在 ISP 输出后另有一级 gamma（典型做法），我们的 tone 表在画面上就被"压平"一次** —— Portrait 的曲线最陡（k4 前 8 项 `2,2,2,3,5,6,8,9`，toe 最黑、mean 616），被压平后的视觉损失最大。这与"Portrait 更灰"的排序**完全吻合**，且与我们的补丁无关。

### 4.3 反证/收敛方法（不需要真机，按顺序做）

1. **算 k_of，确认 Portrait 是否在四档槽内**：`k = (key&7) | ((key>>21)&0x18)`。若 Portrait 的 key 落在 4 个槽之外 ⇒ 它根本没被我们的补丁触碰，B67 的观察就是**相机原生行为**，结论直接闭合（报告只需标注"与补丁无关"）。
2. **查取景帧这几道门的取值**：`0x6046E9B5` 的局部记录（`SP+4`）里 `+0x38` 的 mask、`+0x10` 指向的参数对象首字（`>>4&3`）、`ctx+76` bit3 —— 静态可读 `0x60473994` 写 `buf` 的那两段 241 word 里 `+0x10`/`+0x38` 位置的值（`buf+0x94` 基址 + 偏移），比 ref 就能知道取景帧走"真块/占位/不写"哪一支。
3. **算显示侧是否存在第二级 LUT 的入口**：在 `0x9E00011C`/`0x9E000124`（`0x60477F4C` 与 `0x60479B92` 都写 `*(model+96)/(model+100)`）的消费端看有没有"显示 gamma"选择；若 `*(model+96/100)` 随档变，则 B 成立。
4. 若 1–3 都不能闭合，再上真机探针：读 `0x9E0018CC`（`model+0xA4` 段 2 落点）在 LV 帧与半按帧的内容差异，一次就能定 A/B。

### 4.4 与真机事实的相容性检查

- **B68（四档色度预览+成片一起变、切档不重启）**：与"§3.2 全读到"一致；与 A 的"预览恒为 0/中性"**不一致**，除非切档那一帧门恰好放行（很可能：切档 = 参数变化，5 道门就是为"只在参数变化时重写"而设的）。⇒ **A 只能解释稳态下某几档的偏灰，不能解释 B68** ⇒ A 降为"候选"，B 升为首选。
- **B60（钩 `0x604AA297` 预览变、成片不变）**：自然成立——那个钩只改预览侧的调用点，成片侧的 `0x604B4E29` 没动。**B60 不是"两条链可分离"的证据，只是"改了哪个调用点就只影响哪边"**。旧文档据此下的"可分离"结论要收回。

## 5. 问 4：结论三选一

**选「0 B 自动一致」。**

理由（三条互相独立）：
1. **参数源唯一**：色度/轴块只有一个 getter（`0x604B4B24`），预览与成片在分岔前读到的是同一个池块指针。
2. **代码共享**：取景帧经 class-3 兜底 `0x6046EDC0 → 0x6046EAAF` 进入成片的矩阵/色度链；tone 走唯一上传器 `0x60479960`（钩点在其内部），取景帧直接调它。
3. **真机印证**：B68 四档色度预览+成片同步变化、无需重启；这是"共享"的正面证据。B60 的"只在预览变"可以用"只改了预览侧调用点"完全解释，不需要"可分离"假设。

**不需要为预览做补丁。** 若日后确认 §4.2-B（显示侧第二级 gamma），那也不是 ≤20 B 能修的（要改显示描述符语义，风险高、收益不明）；若是 §4.2-A，则最小补丁是让取景帧必走真块——落点 `0x604B4DFB C9 2E`（`bne 0x604b4e29`）改为 `CA 2C`（无条件 `bra 0x604b4e29`），**2 B**；或 `0x604B4DD7 A0 01`/`0x604B4DD9 C8 06` 改成 `CA 0F`（`bra 0x604b4de8`），**2 B**。两者都在 `0x604B4D25` 里、成片帧也走同一份代码，属于"两边一起动"，**不建议**。
